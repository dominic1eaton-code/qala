The SDE

The Solution Development Environment is the atomic operational unit. SDEs are solution-agnostic — they define the conditions for creating, maintaining, and operating solutions, not the solutions themselves.

One SDE can support a collection of Solutions. SDEs are deployable, configurable, distributable, version-controlled, composable, releasable, and scalable.

Hermetic Build Environments

Every Solution build in qala is executed in a hermetic environment — fully isolated, reproducible build contexts that guarantee consistent outputs regardless of when or where they run.

⊗
Fully Isolated
No access to external network, host filesystem, or ambient credentials during build execution.
⊙
Reproducible
Identical inputs — source, dependencies, environment — always produce byte-identical outputs.
⊞
Environment-as-Code
All build environment definitions are version-controlled and immutable at build time.
⬡
Containerized
Each build executes in a purpose-built, ephemeral container spun up and destroyed per run.
⊡
Dependency Locking
All dependency versions are pinned and cryptographically verified before build execution begins.
◈
Build Attestation
Every build produces a signed SLSA provenance record linking output to its verified inputs.

SLSA Provenance

Supply chain Levels for Software Artifacts (SLSA) is a security framework for build attestation and provenance. Every qala build output carries a signed SLSA record.

The attestation links the build artifact cryptographically to its exact source, build environment definition, dependency lockfile, and toolchain versions — creating an immutable chain of custody from source to deployment.

Before any artifact may be deployed to a TEST or CM environment, the Gateway verifies the attestation signature and rejects unverified artifacts.

Every SDE contains a Solution Toolbox — a governed hierarchy of tools from atomic executables up through composed toolchains.
